# Технические проверки (spike)

Это этап 2.2 (научно-исследовательские работы) по ГОСТ Р 59793-2021: «поиск путей и оценка возможности реализации требований пользователя». Здесь по очереди проверяются самые рискованные технические места, пока не написан продуктовый код. Результаты пойдут в отчёт стадии 2 (`docs/03-roadmap.md`).

Код проверок лежит в `spikes/` и в продукт не переносится. Переносятся выводы, цифры и найденные подводные камни. Основной результат каждой проверки записывается здесь.

## Как вести этот файл

1. Идёшь по порядку S1 → S5. Следующая проверка использует результат предыдущей.
2. Перед началом проверки читаешь её блок: вопрос, откуда он взялся, шаги, критерий успеха.
3. В процессе записываешь цифры и находки в блок проверки и одной строкой в журнал находок ниже.
4. Если находка меняет принятое решение, записываешь новое решение в `docs/decisions.md` (новый D-NNN, старый помечается «Заменено») и ставишь номер в журнал.
5. Когда все пять проверок закрыты, пишешь итог (раздел «Итог») и переносишь в отчёт стадии 2.
6. Для каждой проверки рядом с кодом можно держать `spikes/sN-название/README.md` с командами запуска. Главная запись всё равно здесь.

Критерии успеха ниже — предварительные предложения, их нужно подтвердить числами из ТЗ. Значения, которых пока нет, не выдумываются: сначала измеряешь, потом решаешь, что считать допустимым.

Тестовые видео: свои или открытые лицензии (CLAUDE.md). Например, открытые фильмы Blender; условия лицензии проверь на сайте перед использованием. Нужно как минимум:

- видео примерно 10 минут (предельная длительность, D-005);
- видео 1080p с постоянной частотой кадров;
- видео со снятого на телефон файла с переменной частотой кадров (VFR);
- видео 4K или с кодеком, отличным от H.264, если такое есть.

## S1. FFmpeg: создание прокси

**Вопрос.** Можно ли на машине монтажёра быстро сделать из исходного видео лёгкое прокси, которое проигрывается везде и не теряет точности по времени?

**Откуда вопрос.** D-005: на сервер загружается только прокси H.264, создаётся через FFmpeg на машине монтажёра, длительность до 10 минут.

**Шаги.**

1. Установить FFmpeg и ffprobe. Записать версию.
2. Взять тестовые видео (список выше). Через ffprobe получить частоту кадров, длительность, кодек, признак переменной частоты кадров.
3. Сделать прокси из каждого видео. Проверить варианты:
   - разрешение (например, 720p и 1080p);
   - качество (параметр CRF) и пресет скорости;
   - H.264 + AAC в контейнере MP4;
   - перенос метаданных в начало файла (опция faststart), чтобы видео начинало играть до полной загрузки;
   - частота ключевых кадров (влияет на точность перемотки, см. S2);
   - частота кадров: сохраняется ли исходная, что происходит с VFR.
4. Измерить время, размер, совпадение длительности с исходником, визуальное качество.
5. Проверить запуск FFmpeg из Node.js (как это будет в Electron): запуск процесса, чтение прогресса, обработка ошибок, отмена.
6. Выяснить, как поставлять FFmpeg вместе с приложением и что с лицензией выбранной сборки.

**Трудности:**

- код выхода 0 не означает, что прокси полный (мягкая отмена);
- жёсткая отмена оставляет битый файл;
- единицы `out_time_ms` не соответствуют названию;
- 10-битный исходник без явного формата пикселей даёт профиль High 10;
- в сборке Homebrew нет `drawtext`, и она под GPL;
- синтетические исходники не дают реальной картины по размеру и качеству.

**Решения (предварительный профиль прокси):** если `color_transfer` исходника `arib-std-b67` (HLG) или `smpte2084` (PQ), применяется цепочка перевода HDR в SDR (см. выше); иначе — обычное масштабирование. Далее для всех: первая видео- и первая звуковая дорожка (`-map 0:v:0 -map 0:a:0?`), H.264 High, `-pix_fmt yuv420p`, 720p (`scale=-2:720`), x264 `-preset veryfast -crf 23`, интервал ключевых кадров по итогам S2 (1 с даёт +38 % к размеру на реальном видео), AAC 128k стерео (`-ac 2`), `-movflags +faststart`. Запуск: чтение `-progress pipe:1` по ключу `out_time_us`; запись во временный файл; после завершения проверка через ffprobe (длительность в пределах кадра от исходника) и только потом переименование; при отмене и ошибке временный файл удаляется. Переменная частота кадров приводится к постоянной одним проходом из исходника (`-fps_mode cfr -r <частота>`, частота номинальная — `r_frame_rate` из ffprobe, не средняя), решено по итогам S2 (D-022).

- Номер при паузе надёжно даёт только `mediaTime`, и то не всегда в Safari на 60 к/с. Поэтому плеер после паузы выравнивается на сохранённый кадр.

**Результат:** на видео с **постоянной** частотой кадров перемотка по `currentTime` точна (0 ошибок из 123 при любом интервале ключевых кадров, включая 8,3 с) и воспроизведение сопоставляется с кадрами без расхождений. Точность зависит не от интервала ключевых кадров, а от (1) постоянства частоты и (2) округления времени: перемотка на момент, чуть меньший времени показа кадра, показывает предыдущий кадр. Миллисекунды работают только при округлении вверх и без запаса: на реальных роликах они ошибались; номер кадра с перемоткой на середину кадра работает без правил округления. На переменной частоте перемотка ошибается на 1–3 кадра.

**Трудности:**

- перемотка на точное время показа или на округлённые миллисекунды ненадёжна: микросекундные округления приводят к предыдущему кадру;
- `currentTime` после паузы во время воспроизведения не соответствует показанному кадру (опережает его);
- на переменной частоте результат нестабилен, шаг на кадр по частоте невозможен;
- после перемотки на уже показанный кадр обработчик кадров не срабатывает;
- двухпроходное преобразование к постоянной частоте дало сдвиги кадров (причина не выяснена), однопроходное чисто.

**Решения (D-022):**

- прокси всегда с постоянной частотой кадров, переменная приводится к постоянной одним проходом из исходника;
- комментарий хранит номер кадра; у версии `fps_num` и `fps_den`; время получается расчётом;
- перемотка на середину кадра `(i + 0,5)/частота`, шаг на кадр `i ± 1`;
- номер при паузе берётся из `mediaTime` обработчика кадров, не из `currentTime`;
- интервал ключевых кадров выбирается по размеру и задержке.

## S5. Раздача прокси по HTTP и доступ к видео

**Вопрос.** Как веб-клиент и десктоп получают видео с сервера так, чтобы перемотка работала без полной загрузки файла и ссылка гостя не утекала?

**Откуда вопрос.** D-013: в web видео берётся с сервера по HTTP; D-005: на сервере только прокси; D-014: токен ссылки не должен попадать в логи.

**Почему это отдельная проверка.** Элемент `<video>` не умеет отправлять свои заголовки с токеном, а токен в адресе легко попадает в логи. Это известная трудность, поэтому способ доступа надо выбрать до технического проекта. Проверка добавлена к четырём из дорожной карты по результатам анализа D-013 и D-014.

**Шаги.**

1. Минимальный сервер на FastAPI, который отдаёт файл прокси.
2. Поддержка частичных запросов (диапазоны байт): проверить, что перемотка в середину файла не скачивает всё с начала.
3. Загрузка прокси на сервер: файл на 10 минут из S1, потоковая загрузка, лимиты размера, прогресс.
4. Способы авторизации доступа к видео, сравнить:
   - токен в адресе (риск логов);
   - cookie сессии;
   - краткоживущая подписанная ссылка.
5. Проверить гостевой сценарий: доступ по ссылке из D-014 без регистрации, отзыв ссылки, истечение срока.
6. Проверить, что токен не попадает в логи сервера и в заголовок Referer.
7. Проверить работу в браузере и в Electron.
