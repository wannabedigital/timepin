# Технические проверки (spike)

Это этап 2.2 (научно-исследовательские работы) по ГОСТ Р 59793-2021: «поиск путей и оценка возможности реализации требований пользователя». Здесь по очереди проверяются самые рискованные технические места, пока не написан продуктовый код. Результаты пойдут в отчёт стадии 2 (`docs/03-roadmap.md`).

Код проверок лежит в `spikes/` и в продукт не переносится. Переносятся выводы, цифры и найденные подводные камни. Основной результат каждой проверки записывается здесь.

## Как вести этот файл

1. Идёшь по порядку S1 → S5. Следующая проверка использует результат предыдущей.
2. Перед началом проверки читаешь её блок: вопрос, откуда он взялся, шаги, критерий успеха.
3. В процессе записываешь цифры и находки в блок проверки и одной строкой в журнал находок ниже.
4. Если находка меняет принятое решение, записываешь новое решение в `docs/decisions.md` (новый D-NNN, старый помечается «Заменено») и ставишь номер в журнал.
5. Когда все пять проверок закрыты, пишешь итог (раздел «Итог») и переносишь в отчёт стадии 2.
6. Для каждой проверки рядом с кодом можно держать `spikes/sN-название/README.md` с командами запуска. Главная запись всё равно здесь.

Критерии успеха ниже — предварительные предложения, их нужно подтвердить числами из ТЗ. Значения, которых пока нет, не выдумываются: сначала измеряешь, потом решаешь, что считать допустимым.

Тестовые видео: свои или открытые лицензии (CLAUDE.md). Например, открытые фильмы Blender; условия лицензии проверь на сайте перед использованием. Нужно как минимум:

- видео примерно 10 минут (предельная длительность, D-005);
- видео 1080p с постоянной частотой кадров;
- видео со снятого на телефон файла с переменной частотой кадров (VFR);
- видео 4K или с кодеком, отличным от H.264, если такое есть.

## S1. FFmpeg: создание прокси

**Вопрос.** Можно ли на машине монтажёра быстро сделать из исходного видео лёгкое прокси, которое проигрывается везде и не теряет точности по времени?

**Откуда вопрос.** D-005: на сервер загружается только прокси H.264, создаётся через FFmpeg на машине монтажёра, длительность до 10 минут.

**Шаги.**

1. Установить FFmpeg и ffprobe. Записать версию.
2. Взять тестовые видео (список выше). Через ffprobe получить частоту кадров, длительность, кодек, признак переменной частоты кадров.
3. Сделать прокси из каждого видео. Проверить варианты:
   - разрешение (например, 720p и 1080p);
   - качество (параметр CRF) и пресет скорости;
   - H.264 + AAC в контейнере MP4;
   - перенос метаданных в начало файла (опция faststart), чтобы видео начинало играть до полной загрузки;
   - частота ключевых кадров (влияет на точность перемотки, см. S2);
   - частота кадров: сохраняется ли исходная, что происходит с VFR.
4. Измерить время, размер, совпадение длительности с исходником, визуальное качество.
5. Проверить запуск FFmpeg из Node.js (как это будет в Electron): запуск процесса, чтение прогресса, обработка ошибок, отмена.
6. Выяснить, как поставлять FFmpeg вместе с приложением и что с лицензией выбранной сборки.

**Критерии успеха (предварительно).**

- Прокси проигрывается в Chrome и в Electron.
- Длительность прокси совпадает с исходной в пределах одного кадра.
- Время создания и размер известны для каждого тестового видео; порог допустимого определяется в ТЗ.
- Прогресс и ошибки можно получить из Node.js.

```
zscale=t=linear:npl=200,format=gbrpf32le,zscale=p=bt709,tonemap=tonemap=hable:desat=0,zscale=t=bt709:m=bt709:r=tv,format=yuv420p,scale=-2:720
```

плюс метки цвета на выходе: `-color_primaries bt709 -color_trc bt709 -colorspace bt709`. Скрипт с командами: `hdr-compare.sh`.

**Результат:** создание прокси работает для всех видов исходников, включая 23,976 к/с, переменную частоту и 10-битный HEVC 4K. Длительность совпадает с исходником в пределах одного кадра. 10 минут синтетического 1080p превращаются в прокси 720p за 27,5 с. Прогресс, отмена и ошибки доступны из Node.js.

**Трудности:**

- код выхода 0 не означает, что прокси полный (мягкая отмена);
- жёсткая отмена оставляет битый файл;
- единицы `out_time_ms` не соответствуют названию;
- 10-битный исходник без явного формата пикселей даёт профиль High 10;
- в сборке Homebrew нет `drawtext`, и она под GPL;
- синтетические исходники не дают реальной картины по размеру и качеству.

**Решения (предварительный профиль прокси):** если `color_transfer` исходника `arib-std-b67` (HLG) или `smpte2084` (PQ), применяется цепочка перевода HDR в SDR (см. выше); иначе — обычное масштабирование. Далее для всех: первая видео- и первая звуковая дорожка (`-map 0:v:0 -map 0:a:0?`), H.264 High, `-pix_fmt yuv420p`, 720p (`scale=-2:720`), x264 `-preset veryfast -crf 23`, интервал ключевых кадров по итогам S2 (1 с даёт +38 % к размеру на реальном видео), AAC 128k стерео (`-ac 2`), `-movflags +faststart`. Запуск: чтение `-progress pipe:1` по ключу `out_time_us`; запись во временный файл; после завершения проверка через ffprobe (длительность в пределах кадра от исходника) и только потом переименование; при отмене и ошибке временный файл удаляется. Обработку переменной частоты кадров (сохранять или приводить к постоянной) решить по итогам S2.
