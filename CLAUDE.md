# CLAUDE.md

Инструкции для Claude при работе с репозиторием Timepin.

## О проекте

Timepin — программный комплекс для асинхронного рецензирования видео с привязкой комментариев к таймкоду: desktop-приложение для монтажёра и веб-клиент для гостей и рецензентов (D-013). Проект выполняется как ВКР. Автор — студент, он же разработчик. Сводка: `docs/00-goals.md`.

## Начало сессии

Прочитать в таком порядке, до любых предложений:

1. `docs/03-roadmap.md`, раздел «Где я сейчас»: что сделано и что дальше.
2. `docs/decisions.md`: действующие решения и их статусы.
3. `docs/04-spikes.md`: таблица «Статус» и журнал находок. Здесь итоги технических проверок.
4. `docs/01-process.md`, если речь о стадиях, документах или стандартах.

### Главное за минуту

Если эта сводка расходится с `docs/decisions.md`, прав журнал.

- Тема: программный комплекс для асинхронного рецензирования видео с привязкой к таймкоду (D-001). Рабочее название Timepin.
- Состав: desktop (Electron) для монтажёра, web для гостей и рецензентов, общий React-код в `packages/ui`, сервер FastAPI (D-013).
- Гость входит по ссылке только по имени; регистрация добровольна и даёт проекты, управление комментариями и уведомления (D-014, D-016).
- Границы MVP: D-015. Время хранится в миллисекундах (D-004). Видео до 10 минут, на сервер идёт только прокси H.264 (D-005).
- Desktop: macOS и Windows (D-021). Linux не целевая ОС.
- Процесс: стадии ГОСТ Р 59793-2021 (D-012). Сейчас стадия 1 и параллельно технические проверки этапа 2.2 (`docs/04-spikes.md`).
- Автор не академик, а разработчик: документы для работы пишутся простым языком; академический язык нужен только в пояснительной записке ВКР.

## Рабочая среда

- Машины автора: MacBook Air (Apple M5, macOS) — основная; второй ноутбук с Windows (dual boot с CachyOS Linux).
- На macOS полная сборка FFmpeg: `/opt/homebrew/opt/ffmpeg-full/bin/ffmpeg` (в обычном `ffmpeg` из Homebrew нет `zscale` и `drawtext`). Проверка окружения на любой ОС: `node spikes/s1-ffmpeg-proxy/env-check.mjs`.
- На Windows `.sh`-скрипты запускаются из Git Bash. Переводы строк в репозитории всегда LF (`.gitattributes`).
- Скрипты спайков должны работать на macOS и Windows: без `stat -f`, без `sed -i ''`, без путей `/opt/homebrew` без запасного варианта.
- Тестовые видео не хранятся в репозитории; список и источники — в `README.md`.

## Язык

- Документация, комментарии в коде и сообщения коммитов пишутся на русском.
- Имена переменных, функций, файлов и API-эндпоинтов — на английском.
- Термины из предметной области (раунд, версия, комментарий, таймкод) в коде используются в английской транскрипции или переводе, который зафиксирован в `docs/decisions.md`. Не придумывать новые синонимы.

## Правила работы с документацией

1. `docs/decisions.md` — главный источник решений. Остальные документы должны ему соответствовать. Если документ расходится с журналом, исправить документ, а не переспрашивать.
2. Любое решение, которое меняет стек, модель данных, границы MVP, ЦА или процесс, записывается в `docs/decisions.md` новой записью `D-NNN`. Старые записи не удаляются, а помечаются как «Заменено» со ссылкой на новую.
3. Если решение меняется, обновить все затронутые документы в том же шаге: `00-goals.md`, `01-process.md`, `02-analogues.md`, `README.md`, `CLAUDE.md`. Документация должна читаться как единое целое.
4. Статусы решений: Гипотеза, Принято, Заменено, Отклонено. Гипотеза — рабочее решение, по которому идёт работа. Не переспрашивать его, пока оно не заменено явной записью. Не переводить гипотезу в «Принято» без явного указания автора.
5. Не задавать вопросов о решениях, которые уже записаны в журнале. Вопросы задаются только по «Открыто» в записях и по `00-goals.md` (раздел «Открытые вопросы для руководителя»).
6. Не выдумывать данные исследования. Интервью, опросы, цифры по аналогам и метрики записываются только из реальных источников. Если данных нет, указать «не проверено».
7. Цены и функции аналогов указывать с датой проверки и источником. Маркетинговые страницы вендоров не считаются независимым источником.

## Что нельзя делать без согласования с автором

- Писать продуктовый код приложения до этапа 6.2 (см. `docs/01-process.md`). Одноразовые технические проверки (spike) этапа 2.2 допускаются: они лежат в `spikes/`, не входят в продукт и после проверки удаляются.
- Придумывать этапы или документы без опоры на стандарт. Процесс основан на ГОСТ Р 59793-2021 и связанных стандартах (D-012, D-018). Новые этапы или документы сначала сверяются с `docs/01-process.md` и текстами стандартов.
- Ссылаться на пункты стандартов по памяти. Пункт можно цитировать, только если он прочитан в тексте стандарта. Если файл содержит лишь предпросмотр, это указывается.
- Менять стек, отказываться от Electron или от веб-клиента.
- Добавлять функции, которых нет в границах MVP (D-015): общий чат, покадровый режим как обязательный, браузерный редактор проектов, соавторы.
- Хранить данные проектов только в браузере или только в desktop. Источник данных — сервер (D-016).
- Коммитить и делать push без просьбы автора. Удалённый репозиторий: `git@github.com:wannabedigital/timepin.git` (ветка `main`, лицензия GPL-3.0). Сообщения коммитов на русском, с атрибуцией из системного напоминания.
- Создавать аккаунты в сторонних сервисах (Anketolog, Frame.io и т.п.) и публиковать ссылки на опросы.

## Персональные данные

- В репозиторий не попадают имена, контакты и видеоматериалы реальных респондентов и заказчиков.
- Интервью и результаты опроса в `docs/research/` обезличиваются: роли и опыт без имён и идентификаторов.
- Тестовые видео — только собственные или открытые лицензии. Также допускаются образцы из открытого доступа, выложенные для тестирования (Kodi samples) — по решению автора; при использовании в тексте ВКР и на скриншотах указывается источник. Сами медиафайлы в репозиторий не попадают (`spikes/.gitignore`).

## Стиль документов

- Короткие предложения, без канцелярита.
- Таблицы для сравнений, списки для перечислений, без лишнего форматирования.
- Везде, где есть допущение, писать его явно: «гипотеза», «не проверено», «открыто».
- Открытые вопросы для руководителя собираются в `docs/00-goals.md` (раздел «Открытые вопросы для руководителя»).

## Перед тем как предлагать решение

Сначала прочитать `docs/decisions.md`. Если решение уже есть, опираться на него. Если предлагается изменение, указать, какую запись оно затрагивает и какие документы надо обновить.
